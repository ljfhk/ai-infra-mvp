# 推理网关 / 微服务部署选型速查表

> 适用场景：AI 推理网关（鉴权 / 限流 / 多模型路由 / 调用链追踪）及同类内部系统的部署形态选型。
> 编写背景：在 `localhost` 的服务器巡检系统（Spring Boot 3.2.1 + Java 17 + Vue3）上扩展"推理服务管理"模块时的架构讨论。

---

## 一、核心结论（先看这个）

1. **部署形态核心看规模**，但"规模"不是唯一驱动因素——组织结构、合规/投标要求同样甚至更强地决定形态。
2. **你当前的项目**（182 单机、内部工具、唯一用户、单 vLLM 实例）落在**档1 嵌入式单体**，且长期够用，不需要微服务。
3. **信创 / 等保交付时**：方案文档写"档3 全套微服务"，实际部署可降级为"档2 单网关服务"——既满足投标叙事，又不给自己加运维负担。

---

## 二、三档规模对照表

| 维度 | 档1 · 嵌入式单体（现在就是） | 档2 · 单网关服务 | 档3 · 全套微服务 + SCA |
|------|------|------|------|
| 日活用户 | 1–50（内部工具 / 运维台） | 50–500（多业务线共用） | 1k–100k+（对外平台） |
| 峰值 QPS | < 50 | 50–500 | 500–10k+ |
| 日均推理调用 | < 1 万 | 1 万–100 万 | 100 万+ |
| 开发团队 | 1–2 人 | 多团队 5+ 人 | 多部门、独立发布节奏 |
| 可用性要求 | 挂了重启即可 | 尽量不 down | 99.9%+ SLA |
| 部署形态 | 1 台机 1 个 jar | jar + 1 个独立 gateway 进程 | Nacos + Gateway + 多服务 + K8s |
| 典型例子 | 服务器巡检系统、内部 AI 调试台 | 小团队给内部多业务线供 AI 能力 | 对外 AI 开放平台、多租户 SaaS |

**升级判据**：日活、QPS、团队人数、可用性 SLA 这四个数，任意一个跨过当前档的上限，单体就开始吃力。

---

## 三、真正驱动部署形态的因素（不止用户量）

| 驱动因素 | 说明 |
|------|------|
| **负载规模** | QPS / DAU / 调用量跨过阈值，单体撑不住 → 拆。 |
| **组织结构（康威定律）** | 3+ 团队各自独立发版，单体一个 jar 谁都不敢动 → 微服务才真正划算。与用户量无直接关系。 |
| **合规 / 投标** | 信创、等保、政务项目采购文档白纸黑字写"需采用微服务架构、Nacos 注册中心、Sentinel 限流"。此时部署的是**文档要求**，不是技术需要。 |

> **反直觉真相**：中国政企项目里大量是"**伪微服务**"——拆成一堆 jar，却全部署在同一台机器、无 Nacos、无独立治理，纯粹为方案书好看。这是做信创 / 等保咨询交付时最常遇到的形态。

---

## 四、Spring Cloud Alibaba 能不能用？

**版本兼容性：能用。** Spring Cloud Alibaba 2023.0.1.0 适配 Spring Boot 3.2.x，当前 3.2.1 直接可用，不是障碍。

但组件"能不能塞进现有单 jar"差别很大：

| 组件 | 作用 | 能否嵌入现有单体 jar |
|------|------|------|
| **Sentinel（sentinel-core）** | 限流 / 熔断 / 降级 | ✅ 只是个库，不依赖 WebFlux，直接嵌 |
| **Sa-Token / Spring Security** | API Key 鉴权 | ✅ 都是库，直接嵌（国产，契合信创叙事） |
| **Nacos** | 注册中心 + 配置中心 | ⚠️ 需单独起进程（默认 8848） |
| **Spring Cloud Gateway** | API 网关 | ❌ 独立 WebFlux/Netty 应用，与现有 Tomcat/servlet 同 jar 有 reactor 依赖冲突，必须单独起服务 |
| **Sentinel Dashboard** | 限流规则可视化 | ⚠️ 又一独立进程（默认 8080，会和你 8080 的巡检系统抢端口） |

**结论**：要"用阿里那套的精华"而不"摆其排场"，就在现有单 jar 里加 `sentinel-core`（限流）+ `sa-token`（鉴权），路由转发仍用现有 Controller；**不部署 Nacos、不单开 Gateway、不挂 Dashboard**。

## 五、信创交付策略：写档3，实际档2

| 层面 | 做法 |
|------|------|
| **方案文档 / 投标书** | 写"微服务 API 网关架构"：Spring Cloud Alibaba + Nacos 注册中心 + Sentinel 限流熔断 + Gateway 路由。架构图本身就是交付物。 |
| **实际部署** | 一个 `gateway-service`（Gateway + Sentinel）与现有巡检系统并排跑即可，**不强制**上 Nacos 注册中心、不挂 Dashboard。 |
| **理由** | 满足投标 / 合规叙事；同时不给自己在 182 这类单机环境增加进程与故障点。 |

## 六、落到你的项目

| 用途 | 推荐档 | 具体动作 |
|------|------|------|
| **自己用**（巡检 + 个人推理调试台） | 档1 嵌入式 | 现有 jar 内加 Sentinel-core + Sa-Token；推理模块用已部署的 `/api/inference/*` 接口。 |
| **给客户做交付物** | 方案写档3、实部署档2 | 方案书绘微服务网关架构图；实际另起一个 gateway-service 并排部署。 |

---

## 七、一句话速记

> **真实运行**：单体或同机伪微服务；**方案文档**：全套微服务；**真·高并发**：真微服务 + K8s + 服务网格。
> 你做 AI 落地，最常被问"有没有微服务架构图 + 限流熔断 + 注册中心"——那是给客户看的，跟你这台 182 上实际怎么跑是两回事。

## 附：何时该从档1 升级（自检清单）

- [ ] 峰值 QPS 长期 > 50，且持续增长
- [ ] 要开放给 2+ 个独立团队 / 外部客户调用推理 API
- [ ] 推理网关挂掉会导致非推理业务（如巡检）一起不可用（需故障隔离）
- [ ] 客户采购文档明确要求 Nacos / 微服务架构
- [ ] 需要按模型 / 按租户独立扩缩容

命中任意 2 条 → 考虑档2；命中 4 条以上 → 上档3。
