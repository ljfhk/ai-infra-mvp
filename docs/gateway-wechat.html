SRE 到 AI 部署 · 实战踩坑

给巡检系统手搓一个轻量推理网关：鉴权/限流/路由/追踪全塞进一个 jar

服务器巡检系统跑起来了，vLLM 也接上了，但谁都能裸调 /v1/chat/completions——没鉴权、没限流、没法按模型分流。
本文记录我怎么不引任何新依赖、不拆微服务，在现有 Spring Boot 单 jar 里手搓一个轻量推理网关，把四个能力一次补齐。
最值钱的是中间那个坑：Java 的 HttpClient 默认会偷偷发 HTTP/2 升级头，经 Windows 端口转发后直接把请求打废，vLLM 收空 body 返 400。这个我折腾了大半天才用 tcpdump 抓出来。

📌 阅读对象：在已有 Spring Boot 单体里想加一层 AI 推理网关，又不想上 Nacos / Gateway / Sentinel 那一套的工程师。本文代码可直接复用。

一、先想清楚：要不要上微服务

答案是先不上。

我这台是单机巡检系统，内部工具、唯一用户、单 vLLM 实例——典型「档1 嵌入式单体」。鉴权、限流、路由、追踪这些能力，塞进现有 jar 就够了，引入 Spring Cloud Alibaba 全套纯属给自己加进程和故障点。

真正需要拆微服务的情况：峰值 QPS 长期 > 50、要开放给 2+ 个独立团队、网关挂了会连带拖垮巡检、或者客户采购文档白纸黑字写了「必须微服务架构」。一个都没命中，就老实在单体里做。

⚠️ 一个反直觉真相：国内政企项目里大量是「伪微服务」——拆成一堆 jar，却全跑在同一台机器、无 Nacos、无独立治理，纯粹是为了方案书好看。你写方案可以写全套微服务架构图，实际部署降级成单网关服务，完全不冲突。

二、四个能力怎么落地（零依赖）

不引 Sentinel、不引 Sa-Token，全用 JDK 自带能力 + SQLite：

- 鉴权：API Key 存 SQLite，sk- + 32 位随机数，请求头 Bearer <Key> 校验。

- 限流：自研内存滑动窗口（每秒），全局 QPS + 每 Key 独立 QPS 两层；外加每日 token 限额。

- 路由：gateway_route 表维护 model → vLLM 地址，按模型前缀分流，未命中走默认地址。

- 追踪：每次调用落 inference_call_log，记 model / tokens / 耗时 / 状态码，前端可查。

💡 为什么不用 Sentinel？档1 是单实例，自研一个滑动窗口几行代码就够；Sentinel 的价值在多实例共享限流（要接 Redis / Dashboard），那才是档2 的事。

三、最隐蔽的坑：HttpClient 的 h2c 升级

这是整个网关能不能跑通的决定性 bug。

现象很诡异：代理转发 vLLM 时稳定返回 400，报错 {'type': 'missing', 'loc': ('body',)}——意思是 vLLM 收到的请求体是空的。

排查路径我走了五步：

1. 怀疑 body 丢失，加日志确认网关侧 body 是完整的；

2. 试手动加 Content-Length 头，Java 直接报错「restricted header name」；

3. 改 Controller 的 consumes，没用；

4. 架一个 Python echo server 接收网关转发，发现网关转发本身完全正常——问题出在「网关 → vLLM」这段链路；

5. tcpdump 抓包，终于看到 Java HttpClient 默认发出了 Upgrade: h2c + Connection: Upgrade（HTTP/2 明文升级）。

🚨 根因：我的 vLLM 在 WSL2 里，请求要先经 Windows netsh 端口转发到宿主机再进 WSL。netsh 不会做 h2c 握手，把升级请求原样丢给 uvicorn，uvicorn 解析失败、丢掉 body，于是 vLLM 看到空请求体 → 400。凡是经 netsh / 普通反向代理转发，这个坑都会踩。

一行修复

构造 HttpClient 时强制锁死 HTTP/1.1，400 立刻消失，真实对话返回 200：

1  private final HttpClient httpClient = HttpClient.newBuilder()
2          .connectTimeout(Duration.ofSeconds(5))
3          .version(HttpClient.Version.HTTP_1_1)   // 禁掉 h2c 升级
4          .build();
📌 经验沉淀：凡用 JDK17 HttpClient 经 Windows netsh 或普通反向代理转发，一律显式 .version(HttpClient.Version.HTTP_1_1)，别信默认值。Dify 对接、vLLM 转发同理。

四、请求是怎么走的

一次对话请求的完整生命周期：

鉴权 → 无效 Key 直接 401 → 全局限流（QPS 超了 429）→ Key 级限流（429）→ 按 model 解析路由 → 每日 token 限额（429）→ 强制 stream:false 转发 vLLM → 解析 usage 记日志 → 透传响应。

任意一步不通过就短路返回，干净利落。

滑动窗口限流核心

限流用 ConcurrentHashMap<String, Deque<Long>>，入队时间戳、弹出 1 秒前的、队列长度超阈值就拒绝：

1  private boolean allow(String bucket, int limit) {
2      if (limit <= 0) return true;          // 0 = 不限
3      long now = System.currentTimeMillis();
4      Deque<Long> q = windows.computeIfAbsent(bucket, k -> new ConcurrentLinkedDeque<>());
5      synchronized (q) {
6          while (!q.isEmpty() && now - q.peekFirst() > 1000) q.pollFirst();
7          if (q.size() >= limit) return false;
8          q.addLast(now);
9          return true;
10      }
11  }

五、怎么用：顺手接上 Dify

网关地址就是系统自己的 /api/gateway/v1。想让 Dify 走网关收口鉴权+限流，只需把 Base URL 改掉、配一个网关发的 Key：

1  # Dify 里把 Base URL 从直连 vLLM 改成网关
2  Base URL : http://<巡检系统IP>:8080/api/gateway/v1
3  API Key  : sk-xxxxxxxxxxxxxxxx   # 网关发的 Key，不是 vLLM 的

curl 直测也一样：

1  curl -s http://<巡检系统IP>:8080/api/gateway/v1/chat/completions \
2    -H "Authorization: Bearer sk-3d9c53a344b6bfbb" \
3    -H "Content-Type: application/json" \
4    -d '{"model":"Qwen/Qwen2.5-1.5B-Instruct","messages":[{"role":"user","content":"你好"}]}'
💡 注意把上面的 <巡检系统IP> 换成你自己机器的内网地址；内网 IP 别硬编码真实网段，读者电脑不在你的网段。

六、验证全绿

我写了个 verify_gw.sh 端到端跑了一遍，全过：

- 读配置 200、新建 Key 成功；

- 真实对话 200（Qwen 真回复）、无效 Key 401；

- 限流 qps=1 连发 3 次 = 200 / 429 / 429；

- 调用追踪有记录、前端含网关控制台 UI。

构建用 mvn clean package -DskipTests -o 离线编过，零新增 Maven 依赖，确认档1 设计成立。
